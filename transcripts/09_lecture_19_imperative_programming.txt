15-150 Review Podcast. Episode nine: Lecture 19, Imperative Programming and References.

Most of 15-150 emphasizes pure functions. This lecture deliberately adds mutable state while keeping it visible in the type system.

For any type t, "t ref" is the type of a mutable reference cell containing one t value. Think of a ref as a box whose contents may change.

There are three primitives.

"ref colon alpha to alpha ref" allocates a new box initialized with a value.

"bang colon alpha ref to alpha" reads the current contents.

"colon equals colon alpha ref times alpha to unit" changes the contents and returns unit.

The expression "ref v" evaluates to the box, not to v. Every separate call to ref allocates a distinct cell. A cell is never empty; it always holds one value of its fixed type.

If r has type int ref, "r colon equals 5" changes its contents to five. "bang r" reads five. Assigning a string to r is ill-typed. Mutability is opt-in and type-directed.

Because assignment is useful for its effect rather than its unit result, SML has sequencing with semicolon. "e one semicolon e two" evaluates e one, discards its value, then evaluates and returns e two. Thus "r colon equals 150 semicolon bang r" changes the cell and evaluates to 150.

When tracing refs, maintain two separate pictures.

The environment maps variable names to values, including reference identities.

The store maps each reference identity to its current contents.

Binding a new variable to an existing ref does not copy the box. It creates another name for the same box. This is aliasing.

Pause and predict. Suppose r one equals ref zero, and r two equals r one. After r two colon equals three, what is bang r one?

It is three. Both names point to the same cell.

Shadowing a variable name does not alter old cells or old aliases. Consider:

r one equals ref zero.

r two equals r one.

r three equals ref r one.

Then a new binding shadows r one with ref one.

Finally r two is assigned three.

There are three calls to ref, so there are three allocated boxes. r two still points to the original integer box, now containing three. The new r one points to a different box containing one. r three is a ref-to-ref whose contents still point to the original box. Rebinding a name changes the environment; assignment changes the store.

This leads to two excellent trace checks.

The number of allocated cells equals the number of evaluated ref calls.

A cell's contents change only when a colon-equals assignment targets that cell.

The lecture shows a dangerous factorial using one top-level store ref. The first call may work, but later calls reuse the old accumulated state and return wrong answers. The problem is the lifetime and sharing of the reference.

A better version allocates "val store equals ref one" inside each call to the public fact function, then uses a local recursive helper. Every invocation receives a fresh private cell. To an outside observer, fact behaves like a pure function even though it uses mutation internally.

This is observational purity. A function is observationally pure when clients cannot distinguish it from a pure implementation. A private temporary ref that never escapes can be a benign effect.

References are ordinary values, so they may appear inside recursive datatypes. For example, a mutable linked-list node can contain a ref to the next node. Assignment can then create cycles, something impossible in an ordinary finite immutable recursive value. A cell may ultimately point back to a structure containing that same cell.

Mutation complicates reasoning and parallelism. In pure code, independent computations do not interfere through hidden state. With shared refs, the result may depend on execution order. Parallel reads and writes introduce races unless carefully synchronized.

Still, controlled mutation has practical uses.

A fresh-ID generator keeps an integer ref and increments it on every call. Opaque ascription can hide the fact that IDs are integers, preventing callers from inventing or arithmetically modifying identifiers.

A hook is often a "t option ref." It begins as NONE and is later assigned SOME value, commonly a function. This supports backpatching a dependency that becomes available later.

A global-settings ref avoids threading a configuration argument through many layers of functions, though it makes behavior depend on shared state and should be used deliberately.

Pattern matching can also inspect refs. A pattern such as "ref two" implicitly dereferences a cell and checks whether its contents match two. This works because ref is also a constructor.

Your Lecture 19 checklist:

ref allocates, bang reads, and colon-equals writes.

Assignment returns unit.

Semicolon evaluates left to right and returns the last value.

Variable bindings point to ref values; the store holds mutable contents.

Aliasing means multiple names share one cell.

Shadowing changes which value a name denotes, not old aliases.

A local nonescaping ref can preserve observational purity.

And mutation makes order, sharing, and program history part of the reasoning.
